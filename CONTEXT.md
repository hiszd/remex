# Context: Remex

## Glossary

### User
An administrator of the Remex system. Authenticates via the configurator to create and manage Jobs, Groups, Endpoints, and other domain entities. Every change to the system is attributable to a specific User.

### Server
The central coordinator that maintains encrypted TCP connections with Endpoints. It authenticates Endpoints and provisions their database bearer tokens.

### Endpoint Identity
A unique identity provisioned for each Endpoint device. Currently, the Server generates a **server secret** which the Endpoint uses to authenticate to the Server. The Server then issues a **database bearer token** that the Endpoint caches and uses for direct database access.

Each Endpoint also carries a **machine ID** — the operating system's native unique identifier for the host (e.g., `/etc/machine-id` on Linux). This binds the Endpoint's software identity to a specific OS installation. While stable, it can be regenerated by an administrator with root access.

### Group
A static, user-curated collection of Endpoints. Used to assign Jobs to multiple Endpoints at once. Membership is explicitly chosen by the user and does not change based on Endpoint properties.

### Endpoint
The physical or virtual machine where the Remex software agent is deployed. It executes jobs and reports status back to the core system. *(Note: Currently represented as the `client` table in the database; slated for migration to `endpoint`)*.

### Job
An instruction or payload that specifies work to be done. A Job passes through three states: **Draft** (initial creation, not yet active), **Enabled** (active and assigned to Endpoints), and **Disabled** (paused). Only Enabled Jobs trigger executions on their assigned Endpoints.

A Job's work instruction is composed of a **shell** and a **command** — the command is executed within the specified shell on the Endpoint.

*(Future: Job work instructions should support multiple sources and execution contexts:)*
*( - Download a file or extract a .zip archive onto the Endpoint and execute it)*
*( - Pull artifacts from a remote repository (website, FTP server, network share))*  
*( - Run an arbitrary command (current behavior))*  
*( - Execute within a specific context: User, Administrator, or System)*  
*( - Dispatch behavior based on the Endpoint's operating system)*

A Job has one of three execution modes:

- **Instant** — Runs as soon as the Endpoint receives it.
- **Scheduled** — Runs once at a specific date/time. If the Endpoint is powered off at that time, the execution is skipped.
- **Recurring** — Runs repeatedly on a schedule (e.g., cron expression).

### Assignment
The connection between a Job and its targets. A Job stores its assignments in an `assignments` field containing references to Endpoints and/or Groups. When an Endpoint resolves its work queue, it collects Jobs assigned to it directly, plus Jobs assigned to any Group it belongs to.

### Execution
The localized record of a specific Job running on a specific Endpoint. Tracks the success, failure, or timeout status of that specific attempt.

### Audit Log
A record of every CREATE, UPDATE, and DELETE operation on Jobs, Endpoints, and Groups. Captures who made the change, what changed (before/after snapshot), and when. Intended to be surfaced to Users in the configurator, though this visibility is not yet implemented.

## Open Questions

- **Server role**: The Server currently authenticates Endpoints and provisions database tokens. There is a question of whether the Server can be removed entirely, with the Configurator handling Endpoint provisioning directly. Manual provisioning via the Configurator would not scale to large automated deployments. This trade-off is unresolved.

## Decisions

- **Job Status Computation** (ADR 0001): A Job's current status is determined by looking only at the *most recent* Execution per targeted Endpoint. Historical executions remain available but do not affect the current status.
