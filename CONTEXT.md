# Context: Remex

## Glossary

### User
An administrator of the Remex system. Authenticates via the configurator to create and manage Jobs, Groups, Endpoints, and other domain entities. Every change to the system is attributable to a specific User.

### Host
The physical or virtual machine on which a Remex Endpoint runs. Identified by a **hardware hash** (e.g., `/etc/machine-id` on Linux). A Host may outlive individual Endpoint installations — the same Host gets a new Endpoint identity if the software is reinstalled. Not directly represented as a database record.

### Endpoint
The running Remex software agent on a Host. Has a unique identity (`client_id`, UUID generated at install time). Belongs to exactly one Host. Connects directly to SurrealDB for all operations: authenticates via `hardware_hash` + `secret` after initial enrollment, receives Jobs via live SELECT, produces Executions, and synchronises results to the core database. Limited by granular table permissions to only read jobs and groups, read its own client record, and write executions. *(Note: Currently represented as the `client` table in the database; slated for migration to `endpoint`)*.

### Enrollment Token
A single-use (or multi-use, at admin discretion) 32-character random string generated by the Configurator and stored in the `enrollment_token` table. Presented by an Endpoint on first boot (via CLI flag) to authenticate its initial SIGNUP. Once consumed, the Endpoint's `hardware_hash` + `secret` are used for all subsequent authentication. Tokens can be pre-generated, expired, or invalidated by the admin.

### Group
A static, user-curated collection of Endpoints. Used to assign Jobs to multiple Endpoints at once. Membership is explicitly chosen by the user and does not change based on Endpoint properties.

### Synchronization
The process of pushing locally-cached execution records from an Endpoint to the core database. The Endpoint runs a background sync task that periodically polls its local database for unsynchronized records and pushes them to the remote database. This is a one-way push: the Endpoint never pulls execution records from the core. Synchronization does not cover pulling jobs or group assignments, which are handled by live queries.

### Job
An instruction or payload that specifies work to be done. A Job passes through three states: **Draft** (initial creation, not yet active), **Enabled** (active and assigned to Endpoints), and **Disabled** (paused). Only Enabled Jobs trigger executions on their assigned Endpoints.

A Job's work instruction is composed of a **shell** and a **command** — the command is executed within the specified shell on the Endpoint.

*(Future: Job work instructions should support multiple sources and execution contexts:)*
*( - Download a file or extract a .zip archive onto the Endpoint and execute it)*
*( - Pull artifacts from a remote repository (website, FTP server, network share))*  
*( - Run an arbitrary command (current behavior))*  
*( - Execute within a specific context: User, Administrator, or System)*  
*( - Dispatch behavior based on the Endpoint's operating system)*

A Job has one of three execution modes:

- **Instant** — Runs as soon as the Endpoint receives it.
- **Scheduled** — Runs once at a specific date/time. If the Endpoint is powered off at that time, the execution is skipped.
- **Recurring** — Runs repeatedly on a schedule (e.g., cron expression). *(Note: the `Recurring` variant exists in the type system but the Endpoint does not reschedule jobs after execution. Currently treated as a one-shot Scheduled job — the interval is parsed but never applied. Implementation tracked separately.)*

### Assignment
The connection between a Job and its targets. A Job stores its assignments in an `assignments` field containing references to Endpoints and/or Groups. When an Endpoint resolves its work queue, it collects Jobs assigned to it directly, plus Jobs assigned to any Group it belongs to.

### Execution
The localized record of a specific Job running on a specific Endpoint. Tracks the success, failure, or timeout status of that specific attempt.

### Audit Log
A record of every CREATE, UPDATE, and DELETE operation on Jobs, Endpoints, and Groups. Captures who made the change, what changed (before/after snapshot), and when. Audit entries are created automatically by SurrealDB `DEFINE EVENT` triggers on the `job`, `client`, and `group` tables. The audit log data exists in the database but is not yet surfaced in the configurator UI.

## Open Questions

- **Server crate cleanup**: ADR 0003 replaces the Server with direct DB auth. The `server/` crate and its dependencies need to be removed from the workspace.

## Decisions

- **Job Status Computation** (ADR 0001): A Job's current status is determined by looking only at the *most recent* Execution per targeted Endpoint. Historical executions remain available but do not affect the current status.
- **Direct Database Authentication** (ADR 0003): The TCP Server is removed. Endpoints authenticate via SurrealDB's native `DEFINE ACCESS` rules — enrollment tokens for SIGNUP, `hardware_hash` + `secret` for ongoing SIGNIN. Granular PERMISSIONS on each table limit the endpoint's blast radius. The `blocked` boolean on the `client` table provides immediate admin revocation.
